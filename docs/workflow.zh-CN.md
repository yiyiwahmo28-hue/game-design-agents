# 一个小而完整的游戏设计协作循环

[English](workflow.md)

本项目把 brief 推进为确认的行为、模型或原型，以及可查看的验证证据。五个角色覆盖设计、经济、实现和审查之间的决策交接；每次只启用任务需要的角色。

设计方法受作者的游戏系统工作启发。公开指令和 Lantern Expedition 示例均为全新编写，不含雇主文档、配置或项目资产。

## 使用完整仓库

从新需求开始时，先按[首次使用教程](start-your-game.zh-CN.md)运行
`npm run new -- --name my-game --brief "你的玩法需求" --lang zh`。
它准备独立工作区和完整任务提示；在有文件与运行工具的助手中执行提示，
再启动交付的原型。入口不会自行调用模型或生成游戏。

[雨港救援的完整执行记录](runs/rain-harbor/README.md)展示了原创需求、
设计与交接、首版运行、追加修改、独立审查和可复现证据。
首页回放这些保留产物，并提供真实可玩版本。

说明预期玩家体验、当前行为、希望改变的内容，以及允许助手修改或执行的范围。已有授权在这个范围内持续有效。一次调参不必在每个角色交接时重新审批。

让助手使用 [game-design-team 技能](../skills/game-design-team/SKILL.md)。助手先检查宿主实际提供的委派能力。可调用真正的 subagent 时，可以分配独立分析或互不重叠的编辑；否则由同一个助手按顺序应用不同角色视角，并明确这是自检。

Lantern Expedition 是原创说明性示例：采集获得资源，升级消耗资源并提高采集效率，探索消耗同种资源并推进到目标。修改示例前，先读取仓库当前规则、配置和模拟器接口。本文不规定它们的详细字段或 API。

在完整仓库中，先查看 `package.json`，再使用提供的入口：

```sh
npm test
npm run simulate
npm start
```

这些命令属于示例仓库。只安装技能目录时，没有这些应用程序。命令输出只能支持它实际检查的行为；启动程序不等于已经观察或试玩。

## 只使用可移植技能

把整个 `skills/game-design-team/` 目录及内部引用文件安装到助手支持的 Skills 位置。按该宿主的发现规则加载，再通过名称或宿主支持的调用语法请求使用 `game-design-team`。

技能不依赖仓库顶层文件、软件包、可执行程序、引擎或 MCP 服务。它可以处理你自己的游戏 brief 和现有产物。它提供角色协作指令，不提供 subagent 运行时。

技能内部的 `agents/openai.yaml` 是技能界面元信息，不会注册五个原生 Codex 自定义 agent。本项目没有接入或声称接入该功能。

## 可选 Claude Code 适配

完整仓库的 `.claude/agents/` 包含五个项目角色定义。它们只设置必需的 `name`、`description` 前置字段，模型和工具由宿主决定；正文保留范围、决策和证据约束。

从本仓库启动 Claude Code，要求把适合的任务交给对应角色。只有宿主实际发现并调用了这些定义，才是 subagent 执行。若会话期间刚创建 agents 目录，按宿主的重新加载规则处理。

文件结构和前置字段已对照 [Claude Code 官方 subagent 文档](https://code.claude.com/docs/en/sub-agents) 检查，尚未在 Claude Code 宿主中实跑。这些文件不提供运行时、不固定具体模型，也不授予额外外部操作权限。

## 角色职责

- **design-lead：**负责范围、体验假设、取舍和整合。
- **systems-designer：**负责行为、参数引用和验收场景。
- **economy-designer：**负责资源模型、成长假设和方案后果比较。
- **prototype-developer：**负责通过真实接口实现行为并交付执行证据。
- **playtest-reviewer：**负责检查实际产物和观察，并说明证据局限。

职责按照真实执行路径划分。看似配表的问题可能需要改代码，运行缺陷也可能需要先做规则决策。协调者给受派角色传递相关指令和产物，并划定编辑归属；角色名称不意味着可以任意修改整个业务域。

## 交接与完成

使用[最小交接](../skills/game-design-team/references/handoff.md)：任务基线、决策理由、产物、验收证据和剩余缺口。复用已有上下文，不在多份文档中反复抄写全部规则。

规则变化后，检查与本次任务相关的规格、参数、模型、运行逻辑、玩家反馈和验收场景。记录已同步项及未验证项。遇到尚未选择的重要体验偏好，用具体后果和方案说明差异，不静默替用户做决定。

按[体验审查标准](../skills/game-design-team/references/experience-review.md)，结合任务目标检查节奏、有意义的选择和反馈。参数值与版本约定属于当前任务输入，不是好体验的通用定义。

完成时提供可查看的结果，并准确区分：已规定、已检查、已执行、已观察、有人类试玩支持。模型能暴露取舍，不能证明玩家觉得好玩。说明缺失的运行或试玩证据及下一步。
