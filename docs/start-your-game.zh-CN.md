# 从你的需求，到可玩原型，再到修改验证

[English](start-your-game.md)

带上自己的游戏想法开始。入口命令准备工作目录和完整提示，设计与实现由支持工具的 AI 助手实际完成。入口本身不调用模型，使用的是你在助手中已有的模型配置，相应模型用量按宿主规则计算。

需要 **Node.js 22 或更新版本**、Git，以及能读取文件、编辑代码、运行命令的助手，例如 Codex 或 Claude Code。浏览器工具用于检查画面和实际交互。真实子代理工具是可选项：缺少时，Skill 会明确采用单助手顺序执行角色的模式。

## 1. 准备需求

```sh
git clone https://github.com/yiyiwahmo28-hue/game-design-agents.git
cd game-design-agents
npm run new -- --name my-game --lang zh --brief "做一个采集物资、升级营地和探索的小型浏览器游戏，让玩家权衡先投资效率还是直接推进。使用无需构建的静态 HTML/CSS/JavaScript 原型。"
```

入口和仓库自带的静态服务器都不需要 `npm install`。命令会新建 `runs/my-game/`：

```text
brief.md             完整保留你的原始需求
START_HERE.md        完整提示，包含需求和具体文件位置
delivery.json        预期交付清单，初始状态尚未完成
design/              等待助手写出设计
config/              等待助手创建权威参数
prototype/           等待助手实现原型
evidence/            等待助手记录真实检查与执行过程
```

较长需求可以先保存为 UTF-8 文件，再运行：

```sh
npm run new -- --name my-game-long --lang zh --brief-file ./my-brief.md
```

每次新建请选择未使用的名称。入口拒绝覆盖已有目录，包括空目录。`runs/` 已被 Git 忽略，本地工作不会自动公开。

## 2. 让助手真正完成初版

在助手中打开这个仓库。将入口打印的完整提示粘贴进对话；同一份提示也保存在 `runs/my-game/START_HERE.md`。提示直接指向仓库内的 Skill，这条流程不要求另行全局安装 Skill。

助手应实际交付：

- 设计取舍、规则、体验假设，以及明确标记的临时假设。
- 被运行时代码真正读取的参数配置，以及可玩的实现。
- 与交付文件匹配的启动方法，以及已经执行的行为检查。
- 真实运行记录：实际委派或明确披露的顺序角色模式、决策、缺陷与修复。
- 指向实际产物的 `delivery.json`。

如果存在会明显改变方案的重要偏好，助手可能需要你做决定。已授权范围内的实现和检查应继续推进，无需每次角色交接都确认。没有浏览器工具时，必须说明尚未检查浏览器交互。

## 3. 打开自己得到的原型

对于上述静态浏览器原型，如果沿用默认的 `prototype/index.html` 位置，运行：

```sh
npm start
```

打开[你的本地原型](http://127.0.0.1:4173/runs/my-game/prototype/index.html)，保持服务器运行。仓库首页是公开示例，你自己的游戏在这个单独地址。如果助手使用了其他产物位置或运行环境，请按它实际交付的启动说明操作，并确认它为何偏离了静态原型的要求。

玩一遍主要循环。尝试成功操作、条件不足的操作，以及目标达成或重置。检查界面文字、成本和效果是否与设计一致。能运行之后，仍然需要人来判断是否清晰、是否有趣。

## 4. 提出一次真实修改

初版已经存在后，在同一个对话中给出具体修改，例如：

> 第一次有意义的选择出现得太晚。把它提前，但保持完整升级路径的总价不变。修改前保留可复现的基线，解释哪些规则和文件受影响，同步修改设计、配置、实际行为和检查，展示前后结果与代价。不要把模拟秒数当作人类试玩证据。

选择适合你实际游戏的约束，这个示例不是通用养成指标。助手应保存基线、记录这次真实要求、完成修改，并在说明的假设下比较结果。提前一次选择可能会改变后续节奏，交付中也应展示这些代价。

## 5. 检查交付是否齐全

```sh
npm run new -- --check ./runs/my-game
```

这个检查确认清单记录了执行方式，且五类必需产物的文件存在并非空。初始空工作区会故意检查失败。通过仅表示**文件齐全**：实际执行了哪些测试、浏览器里观察到了什么、哪些检查失败、哪些体验假设未验证，要继续查看验证报告。运行记录应说明助手究竟做过什么。

默认清单期待 `design/design.md`、`config/game.json`、`prototype/index.html`、`evidence/verification.md` 和 `evidence/run-log.md`。助手可以按实际实现更新相对路径；路径必须位于工作目录内，每类必需产物要有自己的文件。`executionMode` 使用 `delegated`（真实委派）、`sequential`（单助手顺序执行）或 `mixed`（混合），与实际执行一致。

## 其他位置与能力边界

`--lang en` 生成英文提示。`--output ./my-workspace` 指定相对当前目录的一个全新目标目录，也接受绝对路径。已有目录、包含 `..` 的穿越路径、经过符号链接的路径会被拒绝。如果目标位于仓库外，需要让助手同时访问工作目录和引用的 Skill，并使用交付的启动说明；仓库静态服务器只提供仓库内部文件。

命令只读取你提供的需求和明确要求检查的交付文件，不读取 `.env`，不联网，不安装工具，也不执行 Agent。新需求能否得到好游戏，取决于需求、设计决策、助手能力与实际验证。这个流程适合小而可检查的玩法；生产级美术、多人基础设施、引擎集成和人类试玩，需要各自的范围与证据。
