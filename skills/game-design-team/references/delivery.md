# A new brief, a playable build, and a verified revision

Use this guide when the task asks for a new runnable mechanic or a complete delivery. A narrow rule change can use existing artifacts and a short final handoff. These are evidence responsibilities, not a required game genre, document layout, engine, or agent count.

## Deliver the first version

1. Preserve the original brief. Separate the intended player experience, observable behavior requirements, reversible assumptions, and open decisions. Explain meaningful alternatives and why the selected design fits the brief.
2. Define a small playable loop with explicit triggers, costs, state transitions, feedback, and end or reset conditions. Specify insufficient-resource and other relevant boundary behavior.
3. Assign concrete artifact ownership. Use actual delegation if available; otherwise disclose sequential perspectives by one assistant. Record real handoffs and reviews, not imagined dialogue.
4. Implement the prototype and its authoritative configuration. Verify that the running code consumes that configuration. Avoid a second set of constants in the presentation layer. Give launch instructions that match the files actually delivered.
5. Execute the implementation in the available environment. Exercise successful actions and consequential rejected or boundary actions. With browser tools, operate the controls and inspect the rendered result and errors. Without those tools, report that browser interaction remains unverified.
6. Inspect the output against the brief. Fix defects inside the authorized scope. Keep preference alternatives and untested experience claims visible rather than grading everything as a pass.

Useful deliverables are a design explanation, authoritative parameters, a playable implementation, a verification record, and a factual run log. Reuse the repository's existing equivalents. A manifest may point to each artifact to expose missing files; a successful completeness check does not prove semantic correctness, execution, or design quality.

## Run a real revision

Preserve a reproducible baseline before changing it: a commit or an explicit snapshot of the relevant source and configuration is enough. Record the actual change request and its source. If the user has not requested a revision, deliver the first version and offer a concrete next experiment; do not manufacture user feedback to complete a story.

Trace the changed rule through its actual consumers: design, configuration, runtime, display, and acceptance cases. Compare before and after under the same stated assumptions, or explicitly report changed assumptions. Explain both the intended gain and a cost or unresolved consequence. Verify preserved constraints as well as changed behavior.

Retain evidence that a reviewer can reproduce. For example, a trace of real actions, test output tied to the relevant revision, and a browser screenshot can complement each other. A screenshot alone does not establish that a configuration drives the runtime. A simulation does not establish human understanding or enjoyment.

## Factual run record

Keep a concise record of:

- The original brief and later change request; confirmed requirements and assumptions.
- Actual execution mode and roles used. Identify self-review when there was no independent reviewer.
- Decisions, artifacts, commands or tool actions actually performed, and observed results.
- Defects encountered, fixes, rechecks, and any still-open decisions.
- Baseline and revised artifact references sufficient to repeat the comparison.
- Checks unavailable in the environment and their practical limits.

Record only events that happened. Do not add invented timings, tool transcripts, model identifiers, conversations, users, benchmark wins, or playtest feedback. Keep private paths, credentials, employer material, and unrelated project data out of public evidence.
